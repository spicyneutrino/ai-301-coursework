# Evidence guide

## Diagnosis and grounding

In eval bundles, read Issue and Repro evidence before Candidate plan's cause. In calib-01, the decisive evidence is successful remote-ref update followed by stale color until re-entry; the plan cites the missed post-push refresh. Good grounding explains those observations rather than assuming push failed. Live evidence lives in the issue body, the student's linked repro comment and the quotes or specific citations inside plan.md and comment.md. A config field proves a field exists, not that a provider runs. A reasoned mechanism with consistent control observations and concrete debug/source tracing can pass without the literal word hypothesis.

## Scope

Read the Candidate plan's change, in/out boundaries and named files against Issue. In calib-01, the push completion callback adds one commits context and excludes status computation and other views. Good scope has a stopping point and only changes needed for the issue or verification. Live sources are the draft scope and file list plus issue requirements.

## Executability

Read Candidate plan's approach and edit locations. In calib-01, pkg/gui/controllers/sync_controller.go and the push completion callback name where and what to edit. Good evidence lets a stranger begin; exact line numbers are not required. Live sources are the draft approach, sequence and prerequisites, not an unquoted implementation elsewhere.

## Test plan

Read Candidate plan's tests beside Repro evidence's steps and expected/actual results. In calib-01, step 3 must change color without leaving the view, with main-panel and force-push checks for the shared callback. Good tests discriminate the old failure from success using real affected code or files. Live sources are the draft commands and expected results, read against the posted repro; stand-in scripts must be replaced by checks through the real artifact.

## Honesty

Read risks, unknowns, confidence claims and Deviations throughout Candidate plan and comment. Compare them with what Repro evidence actually establishes. Good plans label untested causes as hypotheses and resolve or contain material uncertainty. Absence of a dedicated risks section alone is not a failure. Live sources are draft risk/deviation statements and the limits of the quoted reproduction.

## Comms

Read Candidate plan comment against Thread highlights and Repo facts, including CONTRIBUTING requests and AI policy. In calib-01, the review-bandwidth note explains the minimal proposal; there is no stated disclosure requirement. Good comments explain their own cause, change and observable check and follow applicable thread requests. Live sources are issue comments, docs/CONTRIBUTING.md and the draft comment; classmates' plans do not block independent classroom plans. Apply disclosure only when required by policy, and report personal voice rules separately.
